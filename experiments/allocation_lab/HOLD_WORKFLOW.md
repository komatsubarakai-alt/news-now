# 1人運営の保留確認フロー：隔離試作

本番への判断反映・記事統合・事件作成・公開は行わない。PR #17は変更しない。
案Aの4/2/4、追跡保護枠、日額0.20ドル・月額5ドルを変更しない。
ここでの「表示」「公開」はSQLite内の `lab_only` プレビューの状態だけを指す。

## 毎日の作業

1. **確認が必要な案件だけを見る。** 過去の確認履歴は別に保存し、同じ案件IDへの再投入では件数を増やさない。別事件IDの案件を同じURLという理由でまとめない。
2. **発生事実を比較する。** 発生日時・場所・関係者／組織・経緯の各欄を「保存表記の一致／相違／未確認」で表示する。出典URL、引用、対象記事版、出典確認の申告状態を一緒に見る。
3. **判断を記録する。** 同一／別事件／保留を理由とともに記録する。引用がない、本文や出典を確認できない、日付が公開日しかない場合は不明のまま保留する。保存しただけで事件対応や公開は実行しない。
4. **公開前の内容を別に確認する。** 現在の記事版と判断記録に対応するプレビューだけを確認する。この試作の確認は実験表示にしか作用しない。本番の公開承認として利用しない。
5. **疑いがあれば先に表示停止する。** 元記事や判断を削除せず、取消／差し戻し／訂正計画を記録する。訂正後の記事版で再確認し、別の表示確認を行う。

同じ運営者が判断と表示確認を行うことは許容するが、別目的の確認操作を必要とする。同じ人が2回確認しても、独立した2人の検証にはならない。

## 比較の意味と限界

案件番号は比較の根拠に使わない。番号の違いで別事件と判断しない。
同じ発生事実を示す4欄が一致しているのに「別事件」と記録しようとした場合は、矛盾として保留する。
発生日時・場所・経緯の表記が異なり、4欄とも引用と出典確認記録がそろった場合も、別事件を示す**参考情報**として人間へ提示するだけ。
場所の別名、関係者の表記差、逮捕・起訴・判決の日付を、別の事件発生と誤解しない。

`occurred_at.kind=incident` の発生日時だけを比較し、公開日や手続きの日付は発生日時へ自動流用しない。
空欄、引用のない事実、引用中に値がない事実、記事版・対象事件が違う引用は未確認にする。

保存内容との文字列一致と、出典の確認申告は別の状態。見出し一致で本文確認済みにしない。
`operator_checked` は入力された確認申告であり、実際に元記事を閲覧して真偽を検証したというプログラム側の証明ではない。
「公式発表」という種別も保存上の申告であり、ドメイン・発表主体・原文の真正性をこの試作が調査したものではない。
転載2件を独立した2つの裏付けとして数える機能もない。

共有記事の引用には、対象事件ID、記事版ハッシュ、引用元の種類、原文引用とURLを持たせる。
別事件の引用や古い版が混ざれば未確認に戻す。ただし、元記事そのものの記述対象を誤って割り当てた場合まで、文字列照合だけでは検出できない。

## 自動処理と人手の分担

| 処理 | 自動化する範囲 |
|---|---|
| 同じ保存情報の再投入 | ハッシュで検出し、確認待ちを増やさない |
| 引用・版・対象事件の照合 | 保存文字列と参照情報の一致だけを機械確認 |
| 新しい根拠・記事改訂 | 新版を保存し、旧判断の適用と実験表示を停止 |
| 同じ根拠での繰り返し確認 | ローカル確認結果を再利用。APIへ送信しない |
| 判断・根拠不足・矛盾 | 運営者が確認。自動承認しない |
| 確認不能 | 根拠と理由を保管し、対象外や別事件へ自動分類しない |

同じ根拠しかない保留・確認不能案件は、毎日の実行対象には戻さず別の保管一覧に置く。メモだけの変更は履歴へ保存するが、根拠の改訂とは区別して再確認を開始しない。
仮の基準として7日以上の保管はローカルの見直し表示を付けるが、自動再判定や通信は行わない。
誤操作の疑いなどで人が再確認する場合は、明示した理由を別操作として記録する。

新しい記事・引用・事件状態が届けば新版として再確認する。条件が変わっても過去の判断を自動復活させない。
通信枠不足の状態は別のフラグに記録し、記事や判断を保持して再開する。保存済み情報のオフライン確認まで禁止するものではない。

毎回の手動確認カードには最古の実行可能案件を1件確保し、その後は停止中の表示、矛盾・重複の疑い、期限到来などを優先する。
根拠がない最古案件へ無条件にAPIを再送しない。
カードの表示上限は人の作業量の上限であり、AのAI通信枠ではない。

## 認証と確認記録

実装は `MockSession` と `MockIntent` による架空の認証境界だけ。本番ログインではない。
AIのJSONをセッションとして受け付けず、操作目的・対象版・入力内容に対応する別の確認を必要とする。
確認時点で期限・権限を検査する。セッションを記事版の確認結果として流用しない。

本番ではAndroid Chromeのパスキー等による本人確認と、信頼できるサーバー側のセッション管理を設計する。
判断と公開／停止の権限・操作目的を分け、重要操作には現在のプレビューへの確認と必要な再認証を要求する。
認証情報・秘密鍵・セッショントークンをローカルHTMLや公開リポジトリへ入れない。
オフラインのJSONを単に `operator_checked` と書き換えて承認扱いにしない。署名・対象版・権限・有効期限の検証が必要。

SQLiteには入力の版、現在状態、判断・理由・引用・対象事件・操作者・日時・操作IDを別に保持する。
旧判断は追記式の監査履歴へ残し、取消・訂正も新しい操作にする。
監査にはハッシュ鎖を付け、途中の破損を検知する。これは外部の信頼できる署名や悪意ある全履歴改変への保証ではない。

## 公開前後の停止と訂正

判断を保存した後も、現在のプレビューを確認する別操作が必要。
古いプレビュー、古い判断、変更された検証規則での承認を再利用しない。
同じ過去の公開操作を再送しても、取り消した表示は復活させない。

- **訂正・差し戻し:** 現在表示を停止し、再確認待ちへ戻す。
- **誤統合:** 元記事・元事件IDを維持し、分離が必要な理由と対象を記録する。自動分割・再採番は行わない。
- **重複事件:** どの事件との重複を疑うか記録し、表示を止める。自動統合は行わない。
- **訂正後:** 新版の記事と根拠で再判断し、改めてプレビューを確認する。

停止中の出力は「確認中のため表示を停止しています」という状態だけにし、取り下げた内容を出し続けない。
元の表示内容と訂正理由は監査側に残す。
既知の依存関係がある案件は再確認待ち・表示停止にし、無関係な案件は維持する。
依存関係自体が登録されていない場合に影響範囲を完全検出する機能はない。

```sh

```

デモは公開してよい架空データだけを使用する。8件の比較・保管・追加根拠・再開の経路を実行する。取消・訂正は回帰テストで確認する。
模擬操作は、根拠比較のための入力が既に用意された状態で実行する。
内部の操作コマンド数を測定するもので、Androidのタップ数や実際の確認時間の実測ではない。
記事の閲覧、出典の真正性確認、根拠の入力に要する時間は別で、まだ測定していない。

判断記録と表示確認を分けるため、表示まで進める場合は最低でも2つの確認操作が必要。
この試作で確認作業が終わっても、本番の保留が解消された件数として数えない。
新事件ガードへ確認記録を自動変換する処理はなく、実事件への適用は未接続。

## 残る反例と本番導入の阻止条件

同じ事件であるのに、保存された日時・場所・経緯・出典確認申告が一貫して誤っており、運営者もそれを信じると、誤った別事件確認と実験表示が通る。
この反例を再現するテストも含む。テストの成功を、意味上の重複や誤統合が完全に防げたという成果にはしない。

本番接続は不可のまま。少なくとも次が必要。

- 独立した実ニュースの正解付き標本で、出典の誤り・共有記事・日時の混同・転載を評価。
- 本人確認済みの運営者記録と旧判断の取り込み、根拠の訂正・取消しの信頼できる管理。
- 新事件ガード、記事版・引用・別事件制約との厳密な接続。自動承認への変換は禁止。
- 実際の公開承認、停止・訂正・キャッシュ失効と、公開サイトへの反映の検証。
- 本番のバックアップ・復旧・並行処理・監査保護。オフラインSQLiteの試験を実APIの二重課金防止と混同しない。
- スマートフォンでの確認画面と実運営時間の測定。1人運営で処理できる件数は未確認。

API通信・ニュース取得・Actions手動実行は追加しない。実データや確認記録を公開GitHubへ保存しない。

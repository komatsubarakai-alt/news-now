# 通信枠配分の隔離比較実験

本番には接続しない実験。PR #17 の試作品にも接続せず、別の作業ブランチで比較する。
本番の分類・統合・公開・Actions・予算設定は変更しない。

## 実行

リポジトリ直下で、通信なしで架空データの比較を実行する。

```sh
python -m experiments.allocation_lab.run
python -m unittest experiments.allocation_lab.test_allocation -v
python -m unittest discover -s tests -v
```

保存済みスナップショットを使う場合、入力は読み取り専用、結果はリポジトリ外へ指定する。
実データ入り出力を GitHub に追加しない。標準出力へ実データの明細は表示しない。

```sh
python -m experiments.allocation_lab.run \
  --snapshot /private/snapshot \
  --profiles /private/historical-profiles.private.json \
  --private-output /private/results/comparison.private.json
```

`profiles` の形式は `{"profiles":[{"stage":"pair","prompt_bytes":6100,"input_tokens":1800,"output_tokens":550}, ...]}`。
`pair`、`merge`、`status` の各段階が必要。上記数値は形式説明用の架空値。
校正値は保存済み回答と要求ハッシュを完全一致させて取得する。過去の回答を新しい記事の回答として流用しない。

## 比較条件

| 案 | 記事照合 | グループ照合 | 現在地生成 |
|---|---:|---:|---:|
| A：現在の枠配分 | 4 | 2 | 4 |
| B：現在地生成を優先 | 1 | 1 | 8 |
| C：中間配分 | 2 | 1 | 6 |

各値は1回の上限で、実際には既存の金額・通信上限が先に止める場合がある。
ネイティブ `ai_cost_control.reserve/settle` を、一時ディレクトリの台帳に対して使用する。
日額0.20ドル、月額5ドル、日40回、実行24回と、追跡用保護枠（日額0.10ドル・日16回・実行4回）を維持する。
追跡の保護枠を通常処理へ貸し出さない。日付は日本時間で切り替わる。

- 入力データ・順序・金額上限・追跡保護は全案で同じ。
- 現在地生成は既存 `queue_policy.prioritize_groups` の順序を固定し、候補は削除しない。
- 記事版の識別は既存 `article_fingerprint` と一致させ、段階間で二重計上しない。
- 記事照合候補の**件数**は保存済み入力から算出する。照合結果は生成しない。
- 次のグループ照合候補数は、記事照合結果なしには確定できない。比較用に同じ架空の16候補を置く。実測の候補数ではない。
- 記事・グループ照合の入力サイズは工程別の保存回答による中央値で校正する。現在地生成はネイティブのプロンプトを構文解析し、各保存グループの正確なUTF-8バイト数を使う。
- 構文の想定外の変更では停止する。処理スクリプトのトップレベルは実行しない。
- 現在地生成から現在の全事件を渡す処理への変更は行わない。
- 24時間の比較では新規流入を0に固定する。実際の翌日の待機予測ではない。
- AI間隔は6時間、毎時17分の定期実行機会が理想的に利用できると仮定。GitHubの遅延を実測した予報ではない。
- 比較中に同じ作業キーを再選択せず、未照合IDと試行IDを保持する。追加の実験用SQLiteは模擬処理の再起動だけを検証し、実サービスには接続しない。

## 結果の読み方

`estimated_settlement` は保存済み回答の入力バイト対トークン比率・出力トークン中央値を使う**将来費用の仮定**。
`reservation_only` は使用量不明時に予約額を戻さない条件。いずれも実請求額ではない。
予約の累計は日付をまたぎ、精算で解放された額も含むため、1日の上限や請求額と比較しない。

回答成立性は別に評価する。

| モード | 現在地生成の通過 | 全体待機 |
|---|---|---|
| `unknown` | 実回答未取得のため実完了0 | 減らさない |
| `mock_invalid` | 検証不成立を模擬 | 保留として保持 |
| `mock_downstream` | 模擬回答で下流へ移動 | 記事版を保持し減らさない |
| `mock_pass` | 待機を終えられる模擬回答 | 条件付き削減可能数だけ減らす |

`mock_pass` は自動承認・対象外除外・実際の処理完了ではない。実データの正解を与える機能は存在しない。
全モードで `completed_actual_groups=0`、`approval_count=0`、`event_merges=0`。
下流の根拠検証・保存前検証を通過したとの主張はしない。実際の統合・掲載経路を呼び出さないため、精度改善は測定できない。
未照合の増加により同一事件の候補が分散する危険は、本番接続前に別途検証が必要。

## 待機理由

私的な実行ログとの照合結果を `--wait-evidence /private/log-evidence.json` で渡せる。指定しない場合、裏付けのない件数枠・間隔は不明のままとする。結果の `wait_reasons` は記事版を段階間で二重計上しない。不成立回答の抑止は別の補助集計であり、主理由へ加算しない。ログ本文・回答本文をファイルへ出力する機能は設けない。

`explain_wait` は、金額・日次通信・実行通信・件数枠・間隔・根拠不足・検証不成立未分離・不明を区別する。
`budget_deferred` だけでは金額不足としない。現在地生成の4件成功、工程の完全ログ、エラーなし、対象記録の時刻との対応がそろった場合のみ、その実行の件数枠による待機とする。
過去の発生時点の理由まで証明するものではない。複数の制約が重なるため、主理由と横断的な間隔制御・不成立再試行抑止は別に報告する。
古い複合的な根拠エラーを、根拠欠落と形式不備に推測で分割しない。

## 安全範囲・制約

- CLI はソケット接続・AI応答入口を拒否する。外部ニュース取得はない。
- 書き込みは破棄する一時台帳と、明示した私的結果だけ。元記事、記事版、事件ID、判断・引用・履歴を変更しない。
- 既存の不成立キャッシュは採用しない。現行保存データに不成立回答記録がある場合、アダプターは停止し、既存の完全な再試行署名検証を接続する追加作業を求める。条件を推測して抑止解除しない。
- テストの同一条件署名は架空データだけで検証する。記事版・検証条件変更で再試行可能になるが、承認はしない。
- 本番用コマンド・Actionsからの参照は追加しない。シミュレーション結果を本番JSONへ変換する機能もない。
- 月5ドルを使い切った時点で止める。日額上限×日数が月額上限以内とは限らない。
- 優先配分だけでは根拠不足、長期間の流入超過、完結・進展の正しさは解決しない。

本番変更は、この比較PRのマージとは別に設計・安全検証・承認が必要。

実データで実行する場合は前述と同じ `--snapshot`、`--profiles`、`--private-output` を指定する。
出力・SQLiteは公開リポジトリ外に限定し、架空デモ以外の出力をコミットしない。

`session.py` は実験用SQLiteに、未処理を含む作業一覧・記事版の識別情報・旧版の作業記録・試行済みID・予算台帳・操作IDを保存する。
毎回接続を閉じて再開し、一括実行と結果が一致することを確認する。
整数の処理件数を再開位置にせず、要求・記事版・検証版に依存する作業キーで未試行を再取得する。
同じ操作IDは同じ結果を返し、内容の異なる再利用や同じ時間枠の二重処理を拒否する。
保存障害時は台帳と再開位置を同じトランザクションで取り消す。
これは通信を行わない模擬処理の保証であり、実API呼び出しの二重課金防止を保証しない。

記事間の照合対象は配列順序ではなく記事版の組み合わせで識別する。
既存の候補検索が選ばなかった組も別の未照合一覧として保管する。
この一覧は全組み合わせにAI判定を要求するものではなく、未照合を別事件と確定しないための記録。
事件候補も全保存事件IDを未照合として保持し、検索でヒットしない事件を別事件とみなさない。
事件の自動作成・統合を行う命令はこのシミュレーターにない。

### 優先案

- `native`: 元の順序。
- `oldest_follow`: 最古1件を最初に置き、続報候補・進展候補・続報候補、通常記事を順に選ぶ。
- `oldest_progress`: 最古1件、進展候補・続報候補・進展候補、通常記事の順。
- `oldest_due`: 最古1件、期限到来予定に関連しそうな記事・進展候補・続報候補、通常記事の順。

不足枠は再配分し、同一作業を重複選択しない。予算不足時は最古枠も実処理を保証できず、未処理で保持する。
6件枠では基本的に最古1・候補3・通常2となる。候補枠が不足すれば他へ回す。
予定そのものの検索枠と、予定に関係しそうな記事を処理する枠は別。予定検索は実行せず、追跡保護枠を通常側へ転用しない。

続報候補は、媒体名の末尾を除いた保存見出しの8文字以上の共通箇所、または保存URLとの対応による参考情報。
共通箇所と元の保存記事への参照を残すが、本文引用の検証済み根拠には昇格しない。
進展候補は見出しの語句による参考情報であり、否定・過去記事・別事件・記録済み進展の区別は未検証。
期限は保存された予定日を日本時間の日付と比較し、記事公開日を予定日や出来事の発生日に流用しない。
日付不明・状態不明はそのまま保持する。これらの候補に実ニュースの正解ラベルを与えない。
候補件数は重なりがあり、足し算できない。

### 本番導入を阻止する反例

`test_native_boundary.py` は既存テストの架空記事だけで、現行 `event_tracker.merge_incoming` を通信なしで呼び出す。
正しい続報が二重進展にならないこと、根拠不正・予算停止で保留になることを確認する。
同時に、**同じ事件という設定の模擬記事に、AIが誤って `new_event` と回答すると、根拠の文字列検証を通過して重複事件が作成される反例**も記録する。
この反例を再現するテストの成功は、安全性の合格ではない。現行コードの制約を固定するための特性テストである。

この制約はA/C共通。Cによって増える確率や実ニュースの精度差は未確認。
現行の追跡AIには保存済みの既存事件が渡されるが、全候補を実際に比較したことの検証記録はない。
上流の照合枠削減を「既存事件との照合処理そのものの削減」と同一視しない。

追加検証後もCを本番導入候補として推奨しない。
未照合状態と新事件作成の安全条件の接続、重複事件の抑止、独立した正解付き標本での見逃し・誤統合評価が必要。
今回、現行の追跡・検証条件や本番の作成処理は修正しない。

# 本番前の接続リハーサル（架空データのみ）

`test_prelaunch_connection.py` は、既存の隔離用記事・事件・SQLiteに対し、
分野仕分け/代表化の仕事投影から元記事版を選び、既存の根拠・矛盾・保存前検証、
判断同期、公開承認を組み合わせる試験です。新しい本番アダプターではありません。
本番コード/公開/キュー/予算は変更せず、実通信も行いません。
実ニュース・実案件の検証標本、診断、集計、DBはこのPRに含めません。

## 検証する境界

- 代表化前に渡された正式な別事件制約/事件対応が競合すれば、代表化を止める。
- 保存済み運営者判断は元グループ・記事版の指紋/ハッシュに一致したものだけ参照。
  同タイトルの別URLへ判断をコピーしない。保留判断はAIの模擬回答でも上書きしない。
- 仕事投影は事件ID・元グループ・履歴を変更しない。元URL/版ごとに引用を保持する。
- 代表の元版を選んだ後も既存のpreflight/evidence/保存前検証を通す。
  採用後も別の明示的な承認なしには公開しない。
- 同じ内容の別URLを後から処理しても進展を二重計上しない。代表化解除後も同様。
- 記事の更新は、その記事を実際に読んだ判断と承認を失効させる。
  後続記事の判断も、既存事件の文脈として元記事を読んでいれば依存対象になる。
  無関係な事件の確認記録は維持する。
- 本文だけが外部の版管理表で変わっても、タイトル/配信元/公開日の代表化条件は
  同じ場合がある。仕事投影の鮮度を本文や承認の鮮度の証明にしてはいけない。
  本文依存の既存ジョブ/判断/承認は別に再確認待ちにする。
- 同一操作/同一ジョブの再送は二重採用・二重予約をしない。
  採用後に作り直した異なるジョブへ同じ操作IDを流用した場合は安全に拒否する。

## 本番接続を止める条件

1. 未使用標本の使用履歴・根拠・版が確認できず、独立した実データ評価を示せない。
2. 確認済みの対象外条件と、候補/保留を区別できない。未確認の記事を自動削除する。
3. 正式な判断の対象事件ハッシュ/記事版/取消し履歴の照合が未実装。
   元記事と一致する判断でも対象事件の内容が変わっていれば、引継ぎ/再確認が必要。
4. 代表化で省いた元版を、照合済み・根拠確認済み・公開承認済みと扱う。
5. 元記事版の引用/本文の世代と、既存事件の根拠依存を安全検証へ渡せない。
6. 元待機先・事件ID・進展・承認・履歴を可逆に保存できず、部分失敗から再開できない。
7. 月5ドル/日0.20ドル・既存通信回数・処理枠・追跡保護を同時に維持できない。

## 段階的な接続準備案（未実装・承認待ち）

最初は読み取り専用の比較/観察だけにする。対象外候補と代表化の対応表は別保存し、
正本キューを置換しない。候補を保留へ戻せるスイッチと原本への参照を用意する。
導入するなら、比較→運営者確認→限定適用の各段階で別途承認する。

監視するものは、分野別候補/保留、ルール版ごとの遷移、重要記事の見逃し、
代表化の制約競合、判断/承認の失効と滞留、未照合元版数、期限到来予定、
新規AI通信と完全一致キャッシュの区別、予約額と実使用額、日月の残額。
待機数だけを減らす指標にしない。元キューの待機年齢とB案の最古枠も維持する。

ロールバックは新しい仕事投影の使用を止め、元グループと待機先を復元する。
既に検証を通った判断/承認を黙って消さず、取消し履歴を残す別操作として扱う。
切替中の原子的保存・操作ID・予算予約・再起動は、本番アダプター完成後に再検証する。

## 実行

```sh
python -m unittest discover -s experiments/engine_v2 -p test_prelaunch_connection.py -v
python experiments/engine_v2/run_offline.py
```

本文同一性の確認を代表化の必須条件には追加していません。
これらの架空試験に合格しても、本番導入可・実AI精度改善・実料金削減を意味しません。

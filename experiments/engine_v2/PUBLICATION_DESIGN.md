# 公開承認・取消し：隔離試作の設計

本番への公開・承認操作なし。実装対象はPR #17の試作配下だけ。本番移行の可否は今回判断せず、残る阻止条件を記録する。

## 承認の単位

|対象|識別方法|公開上の扱い|
|---|---|---|
|事件の基本情報|事件ID + identity|事件名・カテゴリー・追跡価値だけ。全項目の一括承認ではない|
|現在地など|事件ID + フィールド名|current_stage、summary、latest、next_watch、lifecycle、updated_atを別承認|
|記事|事件ID + 記事URL|その時点の記事内容を承認。共有URLでも別事件の承認は別記録|
|進展|事件ID + 履歴項目のハッシュ|承認した進展だけ出力。表示回数は承認済み履歴から計算|
|予定|事件ID + schedule_id|変更履歴を含む予定項目の内容ハッシュを照合|
|訂正・改訂履歴|事件ID + 履歴項目のハッシュ|承認した項目だけ公開。内部の履歴は消さない|
|完結根拠|事件ID + evidence|完結状態を出すには完結根拠の承認も必要|

事件基本情報と少なくとも1記事の承認が必要。現在地などが未承認なら「確認中」、未承認の進展・予定・訂正は空配列。記事数・進展回数を内部の全件数から流用しない。公開項目中の出典URLと承認根拠のURLも、承認済み記事で閉じる必要がある。

予定のhistoryはその予定項目の一部として明示承認する。進展・訂正・改訂の履歴項目は内容で識別するため、内容変更は旧項目の失効と新項目の明示承認となる。安定した項目IDの導入は将来の改善候補。

## 承認記録

`pub_approvals` に対象、内容・内容ハッシュ、承認者、承認日時、承認理由、根拠と判断IDを保存する。根拠ごとに記事メタデータ版、本文または引用対象の内容ハッシュ、引用原文、根拠ID、変更世代を保持する。

承認するには次の条件が必要。

1. 内容ハッシュが現在の対象と一致する。
2. 引用が保存済みの選択済み記事版に文字どおり存在し、根拠が現在有効である。
3. 公開する進展・予定・完結根拠などに引用が含まれる場合、その引用自体に対応する出典・引用の根拠がある。別の正しい引用で代用しない。
4. 同じ事件について、既存の根拠・矛盾・保存前検証を通過した有効な採用判断がある。
5. 承認対象がその採用判断後の保存内容に存在し、内容も一致する。
6. 根拠がその判断の依存関係に含まれる。既存AIの採用結果や運営者評価だけでは条件を満たさない。
7. 判断取消し・根拠失効・運営者再確認待ち・必要な承認の失効がない。

**すべて模擬承認。** 承認者は `simulation:` で始まる明示ID、承認日時は呼出し側が渡すタイムゾーン付き日時。実在する承認者の本人確認は未実装。原文未取得を文字一致済み扱いにせず、既存7組に未提供の引用・確認日時も作らない。引用一致は真偽や事件同一性の保証ではなく、既存ガードと明示承認が別途必要。

## 状態と履歴

`approved → needs_recheck / withdrawn / superseded` を `pub_state` と追記式の `pub_history` で管理する。新しい承認には新しい操作IDが必要。同じ対象を再承認する場合は置換する旧承認IDを明示する。旧操作IDの再実行は保存結果を返すだけで、失効済み承認を再有効化しない。

`pub_heads` が各対象の最新承認を示す。`pub_dependencies` で前提承認を明示でき、前提の取消しは依存先だけに波及する。`pub_evidence_invalidations` は元の引用を消さず、特定の根拠IDの失効を記録する。その根拠IDの失効を取り消すUIは未実装で、新しい根拠版・判断・承認が必要。

同期処理の訂正・削除・採用・判断取消しから公開承認の再確認処理を呼ぶ。対象内容、記事版、引用、判断・根拠の世代を検査し、不一致だけを再確認待ちにする。公開出力前にも必ず再検査する。元へ戻っても旧承認を自動復活させない。

同じURLを共有していても、事件Aの承認取消しを事件Bへ伝播させない。本文を使用した判断Aと見出しだけを使用した判断Bなら、本文だけの変更はAだけを失効させる。両方が依存する見出し変更なら両方を再確認する。本文を双方が使っている場合、本文全体の版変更では双方を再確認し、未検証で引用を新しい版へ付け替えない。

## 公開取消しの表示設計

事件本体が非表示になっても、模擬的に公開出力へ生成済みだった項目については `publication_status.json` に次を残す。

- 事件ID、対象の種類、対象を識別する不透明なハッシュ。
- 「再確認中」「掲載取消し」「再承認」という履歴、最新承認の現在状態、現在その事件を表示できるか。
- 時刻と定型案内。観測時刻が不明ならnullとし、勝手に現在時刻を入れない。

**取り消した見出し・本文・引用や、非公開の承認者・判断理由は再表示しない。** 承認前の既存34件から、公開したと推測する取消し案内も生成しない。`pub_generated` は隔離先への出力生成を示すだけで、実際の配信・公開を示さない。

画面は、事件が残る場合は「一部情報を再確認中」、事件全体が取り消された場合は事件IDと定型の取消し案内だけを表示する設計。再承認後は現在状態を優先し、古い取消し履歴は折りたたんで表示する。**既存index.htmlへの接続は今回実装していない。** 原文を再露出させない実画面検証が残る。

## 出力の取り違え防止

- `public_events.json`：承認が有効な項目だけの、現行と同じ事件配列。ただし今回はすべて模擬承認なので実配信不可。
- `compatibility_preview.json`：未承認を含む旧方式との比較専用。
- `publication_status.json`：取消し・再確認・再承認の定型状態。
- manifest：ファイル別ハッシュと用途、`scope:isolated_simulation`、`can_publish:false` を必須にする。

`load_approved_simulation` は元SQLiteの現行世代・承認状態と照合し、承認済みファイルだけを読む。比較用JSONの改名、manifestのハッシュ書換え、取消し前の古い出力は拒否する。ファイル名だけを信用して公開する経路を作らない。

## 障害と隔離

SQLiteはメモリーまたは一時ディレクトリのみ。承認・履歴・取消し・根拠失効・失効通知を同じ保存範囲に記録し、途中失敗で全体を戻す。保存後の応答消失は同じ操作IDで再開する。旧判断のキャッシュや予算台帳を承認処理から変更しない。

ファイルは従来の世代別出力と完了manifestで再開する。DBとファイルは一体のトランザクションではない。実公開先・本番承認への接続は存在しない。

## 残る阻止条件

- 本文だけが変わる場合、旧処理がalready_savedを返して新しい採用判断を作れないことを確認。安全基準を迂回せず再承認を止める。本文版を扱う再検証経路が必要。
- 実承認者の本人確認・権限・スマホ管理UI、実配信・取消し通知の接続、実ブラウザー検証。
- 原文・確認日時不足の解消、部分公開時の文章全体の整合性、個人情報や削除理由の表示方針。
- 全運用データの移行、永続DB・バックアップ・障害復旧運用。

本番移行の可否は今回判断していない。

## 通信なしでの再実行

リポジトリのルートで実行する。比較データは評価記録と対応する固定コミット `f4b831d3fa1f514b2713ecca5acebc8a6aaaf99c` の読み取り専用コピー。

```sh
python experiments/engine_v2/run_offline.py
python experiments/engine_v2/publication_replay.py \
  --snapshot /path/to/frozen-read-only-copy \
  --output-dir /tmp/news-now-publication-results
```

実API・外部ニュース取得は実行せず、socketとurllibを禁止する。単独の再現スクリプトも架空の記事・模擬承認しか作らない。
